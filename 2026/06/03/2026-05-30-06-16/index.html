1. synchronized(userId.toString().intern())

为什么要加锁？

防止同一个用户并发重复下单。比如用户快速双击提交按钮，两个请求同时进来，都可能查到 count = 0，然后都插入订单，导致”一人多单”。

为什么锁对象是 userId.toString().intern()？

  • 按用户维度加锁：userId 是 Long 类型，不同用户用不同的锁，用户之间互不阻塞。
  • 为什么用 .intern()？
    userId.toString() 每次可能生成新的 String 对象（即使内容相同，对象地址也可能不同）。intern() 会把字符串放进常量池，保证同一个 userId 对应常量池中唯一的 String 对象。这样 synchronized 才能锁住”同一个用户”。

⚠️ 注意：这只是单机 JVM 锁。如果你的服务部署了多个实例（多台机器），这个锁就失效了，需要改成 Redis 分布式锁。

2.AopContext.currentProxy()

为什么要获取代理对象？

因为 createVoucherOrder 方法上有 @Transactional 注解，事务是通过 Spring AOP 代理实现的。

直接调用的坑：

这是同类方法内部调用（this.createVoucherOrder()），不会走 Spring 代理，导致 @Transactional 完全失效，事务不会开启。

正确做法：

通过 AopContext.currentProxy() 拿到当前类的代理对象，再用代理对象调用，AOP 拦截器才能生效，事务才会开启。

使用 AopContext 需要在类上加 @EnableAspectJAutoProxy(exposeProxy = true)，或者在启动类配置 exposeProxy = true。

3. 为什么锁要包裹代理调用？

执行顺序：

  1. 先拿到用户级别的锁（同一用户串行）
  2. 再走代理开启事务
  3. 执行事务方法（查订单 → 扣库存 → 创建订单）
  4. 事务提交后，锁释放

这样保证：

  • 同一用户的并发请求被锁排队
  • 事务在锁的保护下执行
  • 不会出现”都查到没订单，然后都插入”的并发问题

总结

synchronized 锁住同一个用户，防止并发重复下单；AopContext.currentProxy() 拿到代理对象，让内部方法调用也能走 Spring AOP，从而使 @Transactional 事务生效。两者配合，实现”单机版”的一人一单 + 事务安全。

集群下的线程并发问题

在之前我们使用synchronized实现了用锁解决单机情况下的一人一单安全问题，但是在集群模式下就不行了。

因为synchronized就是利用JVM内部的锁监视器来控制线程的，而在JVM内部，由于只有一个锁监视器，所以只有一个线程可以获取锁，可以实现线程的互斥

当有多个JVM的时候，会有多个锁监视器，导致多个线程获取到锁，没有办法实现多JVM进程之间的互斥

Redisson分布式锁主从一致性问题

**问题描述：**在多台redis中分为主节点（负责写）和从节点（负责读），当java请求获取锁成功后在主节点和从节点进行同步时主节点发生故障，会让某个从节点充当主节点，但是因为同步尚未完成，导致锁丢失。

**Redisson解决：**将多个redis节点独立起来，请求方式为依次向每个redis节点获取锁，能够从每个节点获取锁才是成功，若还是觉得不够安全，则将这些redis添加主从结构

总结：

1.不可重入Redis分布式锁：

  • ◆ 原理： 利用setnx的互斥性；利用ex避免死锁；释放锁时判断线程标示
  • ◆ 缺陷： 不可重入、无法重试、锁超时失效

2.可重入的Redis分布式锁：

  • ◆ 原理： 利用hash结构，记录线程标示和重入次数；利用watchDog延续锁时间；利用信号量控制锁重试等待
  • ◆ 缺陷： redis宕机引起锁失效问题

3.Redisson的multiLock：

  • ◆ 原理： 多个独立的Redis节点，必须在所有节点都获取重入锁，才算获取锁成功
  • ◆ 缺陷： 运维成本高、实现复杂

这段代码是一个高性能秒杀下单的实现，核心思路是 “Redis 做资格预判，阻塞队列做流量削峰，异步线程做数据库写”。下面逐段详细拆解：

整体架构设计

用户请求
↓
seckillVoucher() [主线程，同步]
├─ 执行 Lua 脚本（Redis 原子判断：库存>0 且 未购买？）
├─ 若通过，生成订单对象 → 丢进 BlockingQueue
└─ 立即返回订单号（不碰数据库）

VoucherOrderHandler [后台单线程，异步]
├─ 死循环 take() 从队列取订单
├─ Redisson 分布式锁（一人一单）
└─ 代理对象调用 createVoucherOrder()（事务）
├─ 查重（一人一单）
├─ 扣减库存（乐观锁 CAS）
└─ 写入订单表

逐段详细解释

1. 依赖注入

2. Lua 脚本静态加载

作用： 类加载时一次性读取 resources/seckill.lua，避免每次请求都读文件 IO。

Lua 脚本在 Redis 里是原子执行的，这步就把高并发下的库存判断和重复购买判断解决了，不用数据库扛并发。

3. 阻塞队列 + 异步线程池

组件 作用
ArrayBlockingQueue 有界队列（容量约 100 万），内存级缓冲。主线程把订单对象扔进来，消费线程慢慢取。
newSingleThreadExecutor() 单线程线程池，保证从队列取出的订单是串行处理的，避免多线程竞争数据库连接池。

为什么用单线程？

  • 秒杀场景下，数据库写入是瓶颈，单线程顺序消费已经够用了（毕竟 Redis 已经挡了 99% 流量）。
  • 多线程并发写反而容易把数据库连接池打满，且增加锁竞争复杂度。

4. @PostConstruct 启动后台线程

Spring 生命周期： 类构造完成、依赖注入完成后，自动启动后台线程开始监听队列。

5. 内部类：VoucherOrderHandler（消费者）

  • orderTasks.take()：阻塞式获取，队列空时线程休眠，不占用 CPU。
  • while(true)：常驻内存，持续消费。

6. handleVoucherOrder：数据库写入前的并发保护

为什么这里还要加锁？

Lua 脚本在 Redis 里做了预检，但 Redis 和数据库是两个系统，存在竞态窗口：

  1. 用户 A 请求通过 Lua，进入队列
  2. 用户 A 又点了一次，通过 Lua，进入队列（Redis 到数据库异步处理有延迟）
  3. 两个订单对象都在队列里，消费时如果不加锁，可能都查到 count=0，然后都插入

Redisson 锁确保同一用户的订单在数据库层面串行处理，实现真正的”一人一单”。

7. seckillVoucher：主流程（入口）

关键设计：

  • 资格判断在 Redis 完成，响应时间 < 10ms，用户体验极好。
  • 数据库操作异步化，避免用户等待 200ms+ 的数据库事务。
  • 立即返回订单号，前端可以拿着订单号轮询查询订单状态。

8. createVoucherOrder：数据库事务层

为什么 Lua 判断了库存，这里还要 gt("stock", 0)？

  • Lua 里扣的是 Redis 里的缓存库存，数据库里的真实库存可能因缓存不一致或其他管理后台操作而不同。
  • gt("stock", 0) 是数据库乐观锁，确保 stock - 1 只在 stock > 0 时成功，防止超卖。

为什么是 void 而不是 Result？

  • 这是异步调用的内部方法，成功失败都靠日志记录，不需要向前端返回（前端已经拿到订单号走了）。

Lua 脚本 Redis 原子判断库存+防重，抗高并发 直接查数据库（扛不住）
BlockingQueue 内存级削峰，解耦 Redis 判断和数据库写入 MQ（RabbitMQ、RocketMQ）
单线程消费 顺序处理，降低数据库连接压力 多线程 + 数据库连接池调大
Redisson 锁 异步处理时，同一用户串行，防止队列内重复订单 数据库唯一索引 (user_id, voucher_id)
AopContext 内部类异步调用时，让 @Transactional 生效 注入自身代理 @Autowired IVoucherOrderService proxy

总结

秒杀业务的优化思路是什么？

① 先利用Redis完成库存余量、一人一单判断，完成抢单业务

② 再将下单业务放入阻塞队列，利用独立线程异步下单
